# Coordinator lessons

Each rule came from a real incident in a project run with about fifteen lanes over several days. Where the human spoke, their exact words are quoted: they are the source of the rule, so keep them.

1. **The coordinator doesn't do hands-on work.** After a compaction, one ran infrastructure quota, egress and secret changes itself. The human: "you're doing work again - you're the orchestrator, you're not an engineer." Route every hands-on step to the owning lane or a fresh session. Your own checks are short and read-only.
2. **Merging is the coordinator's job.** The human: "you're in charge of merging - why are you asking me?" and "IMHO merge as soon as the reviews are complete". Never ask the human about a merge.
3. **A flake on the base branch doesn't freeze merges.** One coordinator paused every merge for a flake that was already on main, and the human merged PRs themself ("i did some merging for you - i was done waiting"). Fix the flake in its own PR and keep merging. Never rerun to get green: a test that fails and then passes is a bug. Only a red base branch stops merges.
4. **Archive lanes promptly.** The human: "i just archived a bunch of session - you're not doing it, so i did it". When a lane's post-merge list is empty, archive it in the same sweep.
5. **Use each side's native messaging.** Sessions of the same kind talk over that kind's own session messaging; the human: "for claude <..> claude we should use native claude functionality". A relay is only for crossing kinds (Claude to Codex), and each lane's channel is written in the ledger ([channels.md](channels.md)).
6. **Always re-arm the watcher, and acknowledge what you handled.** A missed re-arm left a set of workers idle for hours. If a relay needs a watcher or an acknowledgment, re-arm after every inbox, and acknowledge every message you handled (unacknowledged ones are redelivered).
7. **Asks to the human are short.** A 1,600-word issue thread buried a one-line decision. Each ask is one short, standalone, latest comment on the human's issue, assigned to them, with the decision and its options.
8. **Compaction loses focus.** The human: "this is why i asked if we should set a goal because you're losing focus after each successive compaction". Keep the goal set, and keep durable notes (the ledger) outside the context. After a compaction, read the goal and the ledger before anything else.
9. **No permission laundering.** Never relay the human's approval to satisfy a lane's permission check: a lane's step that needs their go-ahead needs it typed in that lane. And never run a step another session was refused. If a session was refused something, the refusal stands until the human lifts it where it was refused.
10. **Start sessions on the human's turns only.** Starting a session is refused (or should be treated as refused) on turns another session or an automated event started. Propose instead, or wait for the human's next turn. A self-contained task gets a fresh session in its own worktree, started without asking, once the human has given standing approval for it.
11. **Deploy only a commit that has everything.** In a burst of merges, newer runs supersede and cancel older ones, so the newest commit may have no finished artifacts. Deploy the newest commit that has all its artifacts built and a green run, and let merges keep flowing: a pinned commit can't be changed by later merges.
12. **Batch similar tickets.** The human: "remember to batch up as many similar ones as possible... we could do 10 in the same session if it's all the same times". One lane can take a batch of same-shaped tickets.
13. **A delegated approval has edges.** When the human delegates an approval (customer copy, for example: "i'm OK with you approving copy, if in doubt ask advisor"), write down what stays theirs: a new price, new terms, scope, anything legal. A string that only restates what the human already set is ordinary work; one that introduces something new goes to them. Don't send the human things they delegated either: "honestly, those strings are fine - but i don't know why you think i need to approve them".
14. **Subagents are still your session.** A coordinator gave two flake fixes to subagents it spawned. Their PRs and their CI and review events bound to the coordinator's own session, and it ended up relaying fixes. The human: "again - why are you fixing PRs? you are the orchestrator NOT an engineer". Anything that ends in a commit or PR goes to a separate worker session that binds the PR to itself. Subagents are for short read-only checks.
15. **A cap in a brief stops nothing.** Paid runs need a cap the provider enforces, a trial run first, a projection from the trial's actual spend, and a stop if the projection is over ([routines.md](routines.md#paid-runs)).
16. **A tree pass that moves files must be sequenced with open PRs.** Moving or renaming story files that several open PRs still edit makes every one of them conflict. The ticketer lists the open PRs touching a file before it moves it, and the coordinator sets the order ([routines.md](routines.md#tickets)).
