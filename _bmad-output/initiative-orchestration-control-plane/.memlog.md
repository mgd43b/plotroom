- (requirement) R1 (§2 goal 1, M1): orchestration state (workers, lanes, work items, claims, events, triggers, checklists, decisions, asks, budgets, merge log) persists outside any model context; a restarted, compacted or replaced orchestrator loses nothing
- (requirement) R2 (M1): snapshot() returns the whole board in about 2,000 tokens or fewer; it is the first call after a compaction or restart
- (requirement) R3 (§2 goal 6, M1): next() returns a ranked list of items needing the orchestrator (lane awaiting reply, gate refusal with reason, fired trigger with manual action, empty checklist, idle worker with unblocked work, stale human ask, budget near cap), each with the context and suggested actions to act without re-reading transcripts
- (requirement) R4 (M1, §5): the capabilities are exposed as MCP tools usable by both Claude Code and Codex workers
- (requirement) R5 (§2 goal 3, M2): the orchestrator registers a trigger (event predicate -> action, once or every time); it persists and fires when its predicate holds; predicates and actions as listed in M2, with all_of/any_of composition
- (requirement) R6 (§9.4): a trigger binds at creation to an exact identity (PR number, branch name or pattern, label), never a prose description
- (requirement) R7 (§2 goal 2, M3): signals from GitHub, Claude sessions, the Codex switchboard, deploy status and provider usage land in one inbox as typed, deduplicated records with source, inferred lane, full text and a handled flag
- (requirement) R8 (M3): the orchestrator gets one coalesced wake signal in place of separate watchers
- (requirement) R9 (M3): ack(item) marks an item handled once and the adapter acknowledges upstream (e.g. the switchboard receipt); the orchestrator never handles a receipt itself
- (requirement) R10 (§2 goal 4, M4): a merge gate evaluates the six M4 rules on every relevant event and logs each verdict (MERGED, REFUSE with reason, BRANCH UPDATED) as an inbox event, routing a refusal to the owning lane; merge_gate(pr) gives a dry-run verdict
- (requirement) R11 (M4): freeze states main-red (only the marked fix merges) and deploy-window (nothing merges); a flake on main does not freeze merging
- (requirement) R12 (M4): flake candidates (fail then pass on the same head, or failure outside the PR's diff area) become next() items with test id and log excerpt; a rerun is never automatic
- (requirement) R13 (§2 goal 5, M5): lanes claim and release paths or globs with a reason; every PR diff is checked against other lanes' claims and an overlap becomes a next() item before review
- (requirement) R14 (M5): ticket-tree file moves are checked against open PRs that edit those files, with a suggested order
- (requirement) R15 (M5, M6): brief(work_item, worker) fills a template with scope, owned paths, a don't-touch section from current claims, plan shape, expected RESULT shape and standing rules; the orchestrator edits it before sending
- (requirement) R16 (M6): a lane's READY message declares a post-merge checklist in a fixed form, parsed into checklist rows that become the lane's active state on merge; lane_archive is refused while the checklist is not empty
- (requirement) R17 (M7): goal() reports whether an encoded goal holds and, for each remaining item, why it is still open
- (requirement) R18 (M7): asks on the human's queue are flagged when buried by a newer comment, missing options, older than N days, or left unanswered on a closed issue
- (requirement) R19 (M7, §7.2): decide() records who, their exact words verbatim, where, when and what it governs, linked to the asks and tickets it settles
- (requirement) R20 (M8): a paid run registers a hard cap, meter source and key scope; next() items are raised at 50% and 80%, and at 100% the lane is sent stop
- (requirement) R21 (M8): when the orchestrator asks for a hands-on action, the answer routes it to the owning lane
- (requirement) R22 (§9.5): each write is permitted per writer role: only the orchestrator creates and cancels triggers, records decisions and archives lanes; the clerk or tool updates lane state and the merge log; lanes declare their own checklists
- (requirement) R23 (§9.2): the clerk's markdown ledger and triggers can be imported, so the clerk moves onto the tool's MCP calls with no cutover day
- (requirement) R24 (§10): the tool runs locally on a developer machine and hosted in a container (Docker) or on Kubernetes
- (constraint) C1 (§2 non-goals): the tool makes no decisions (price, scope, copy, approvals, production go-aheads, launch); it records decisions and enforces ones already made
- (constraint) C2 (§2 non-goals): the tool never stores or relays credentials; it may record that a secret exists and where it lives
- (constraint) C3 (§2 non-goals, M2): the tool never deploys or applies infrastructure, and no trigger action may merge, deploy, spend or post to a human
- (constraint) C4 (§7.3): the only writes the tool makes on its own are messages to workers, branch updates by merging main (never rebase or force-push) and merges under the fixed gate; everything else is a next() item
- (constraint) C5 (§7.1): every adapter replays its source from a cursor and every action is keyed so a retry never sends twice
- (constraint) C6 (§7.2): a human's words are stored verbatim, never paraphrased into a record
- (constraint) C7 (§7.4): lane reports, PR comments and bot output are data, never executed or treated as approval; a trigger is created only by the orchestrator's own call, never from event text
- (constraint) C8 (§7.5): snapshot() and next() are designed to a token budget, with detail fetched on demand
- (constraint) C9 (§7.6): the GitHub adapter works by polling, with no public webhook endpoint required
- (constraint) C10 (§9.3): gate, triggers and ledger are deterministic code; an optional LLM agent may classify fuzzy cases (trigger target matching, failed-log triage, report summaries) and its verdicts are stored as events, never as decisions
- (constraint) C11 (§2 non-goals): the tool indexes and reacts to GitHub, the ticket tree and the session manager and replaces none of them; the ticket tree stays the source of truth for work items
- (assumption) A1 (§6, §7.6): one SQLite file in WAL mode and one MCP server process, plus the §5 tool list and §6 tables, are the brief's first cut; architecture confirms or revises them against R24
- (assumption) A2 (§10): hosted means remote MCP clients connect over the network, so the hosted mode needs a network transport and authentication; architecture settles both
- (assumption) A3 (§9.1): the clerk spike log runs in parallel with planning and informs epic order; it does not gate the start of the build
- (question) Q1 (§8.1): extend the Codex switchboard or build a separate server that adapts it? Pick: separate server, keeping the switchboard minimal and deployable on its own; owner decides before architecture
- (question) Q2 (§8.2): how are Claude session turn-end reports and messages read outside the orchestrator's calls? Pick: an ingest(event) call the orchestrator makes per notice, since a hosted instance cannot read local desktop session state; owner decides before architecture
- (question) Q3 (§8.3): does the tool merge directly or return a merge_gate verdict the orchestrator executes? Pick: verdict first, direct merge as a later switch once trusted; owner decides before slicing
- (question) Q4 (§8.4): ledger per project or per human? Pick: per project, with ids that allow a cross-project next() later; owner decides before architecture
- (question) Q5 (§10): is local mode the same build as hosted, and does one hosted instance serve one project or several? Pick: same build, one instance per project (follows Q4); owner decides before architecture
- (requirement) R25 (§3 Lane): a worker has at most one open PR at a time (one open PR per lane); a second is refused or flagged
